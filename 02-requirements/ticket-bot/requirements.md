# Требования к телеграм-боту для отслеживания субсидируемых билетов

**Дата:** 01.04.2026  
**Проект:** Telegram-бот для жителей Дальнего Востока

## 1. Цели и задачи проекта

- **Бизнес-цель:** Автоматизировать процесс поиска и уведомления о субсидируемых билетах через удобный интерфейс Telegram, сократив время пользователя на ручную проверку.

- **Целевая аудитория:** Жители Дальнего Востока, имеющие действующую прописку.

- **Ключевые метрики успеха:** Увеличение числа пользователей бота. Получение прибыли. Количество активных сценариев больше 10.

## 2. Стейкхолдеры

**Стейкхолдер: Владелец проекта**
Боль: Нужно окупить разработку и обслуживание сервера.
Цель: Монетизировать сервис и окупить разработку.

**Стейкхолдер: Зарегистрированный пользователь**
Боль: Трачу много времени на ручную проверку, часто пропускаю билеты, так как их быстро разбирают.
Цель: Создание сценария отслеживания появления субсидируемого билета по нужным параметрам.

**Стейкхолдер: Администратор**
Боль: Бот работает постоянно, в случае если в API произошёл сбой, то сценарии не обрабатываются оперативно.
Цель: Получать уведомления об ошибках системы, чтобы иметь возможность быстро внести исправления. Иметь дашборд с метриками работы бота

**Стейкхолдер: Администратор баз данных**
Боль: Много сценариев.
Цель: Обрабатывать только актуальные сценарии по датам.

## 3. Функциональные требования

### 3.1 Управление сценариями

1. **Создание сценария:** Система должна позволять пользователю создать новый сценарий поиска с указанием:
   - Город вылета (выбор из справочника)
   - Город прилета (выбор из справочника)
   - Диапазон дат (от 2 до 14 дней)

2. **Просмотр сценариев:** Система должна предоставлять пользователю список всех его сценариев с указанием статуса (активен / неактивен).

3. **Редактирование:** Система должна позволять пользователю редактировать параметры существующего сценария.

4. **Удаление:** Система должна позволять пользователю удалять сценарий.

5. **Активация/деактивация:** Система должна позволять временно приостанавливать сценарий без удаления.

### 3.2 Уведомления

6. **Отправка уведомлений:** Система должна отправлять уведомление пользователю при появлении билетов, соответствующих его сценарию.

7. **Содержимое уведомления:** Уведомление должно содержать:
   - Маршрут (город вылета → город прилета)
   - Дату вылета
   - Цену билета
   - Ссылку на покупку

8. **Административные уведомления:** Система должна отправлять администратору уведомления о:
   - Сбоях API источника билетов
   - Критических ошибках бота
   - Достижении пороговых метрик (например, 500 активных сценариев)

### 3.3 Справочники и администрирование

9. **Управление справочниками:** Система должна предоставлять администратору возможность добавлять, редактировать и удалять города в справочнике.

10. **Просмотр всех сценариев:** Система должна предоставлять администратору возможность просматривать все активные сценарии всех пользователей.


## 4. Нефункциональные требования

- ### Производительность
- Частота проверки билетов по активным сценариям — каждые 30 минут
- Время отклика на команды пользователя — не более 5 секунд
- Поддержка одновременной работы — не менее 100 активных сценариев

### Надежность
- При недоступности API источника — повторные попытки каждые 10 минут
- Уведомление администратору после 3 неудачных попыток подряд
- При восстановлении API — автоматическое возобновление проверок
- В случае падения бота — восстановление работоспособности в течение 24 часов с сохранением всех сценариев

### Безопасность
- На сервере хранятся только Telegram ID пользователя и его сценарии
- Личные данные (ФИО, телефон) не запрашиваются и не хранятся
- Данные не передаются третьим лицам

### Удобство использования
- Интерфейс — Telegram (кнопки, команды)
- Язык интерфейса — русский
- Встроенная инструкция по использованию по команде /help

### Масштабируемость
- Архитектура должна позволять увеличение частоты проверок без потери производительности

## 5. Ограничения и допущения

### Технические ограничения
- Источник билетов — API конкретной авиакомпании / агрегатора (уточняется)
- Лимит API источника — не более 50 запросов в минуту
- Бюджет — бесплатный хостинг на начальном этапе 

### Допущения
- Пользователи имеют аккаунт в Telegram и умеют им пользоваться
- API источника билетов стабилен и имеет документацию
- Пользователи готовы оплачивать создание сценария (50 руб./сценарий)
- Справочник городов ограничен утвержденными правительством маршрутами.

## 6. Критерии приемки

1. ✅ Уведомление отправляется **только** при появлении билетов, соответствующих критериям сценария (маршрут, диапазон дат, субсидируемый тариф).
2. ✅ Пользователь может создать новый активный сценарий, указав город вылета, город прилета и диапазон дат.
3. ✅ Пользователь может просмотреть список всех своих сценариев с указанием статуса.
4. ✅ Пользователь может отредактировать существующий сценарий.
5. ✅ Пользователь может удалить сценарий.
6. ✅ При сбое API администратор получает уведомление в течение 5 минут.
7. ✅ Все действия пользователя фиксируются в логах для отладки.
8. ✅ Справочник городов пополняется через админ-интерфейс.
9. ✅ После перезапуска бота все сценарии сохраняются и продолжают работать.

## 7. Рефлексия

**Что было сложнее всего?**
Сложнее всего было формализовать бизнес-цель в измеримые метрики. Поняла, что «получение прибыли» — это слишком размыто, нужно конкретное значение.

**Что узнала о своем проекте?**
Поняла, что для реализации потребуется:
- Справочник городов
- Механизм периодической проверки (cron)
- Обработка ошибок API
- Логирование всех действия для отладки

**Какие вопросы остались?**
- Как технически ограничить количество сценариев на пользователя?
- Как организовать оплату за создание сценария?

**Что можно улучшить в следующих итерациях?**
- Добавить автоматическое удаление неактивных сценариев старше 30 дней
- реализовать возможность поиска билетов с указанием верхней границы цены.
